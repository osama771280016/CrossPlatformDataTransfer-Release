# تدقيق المشروع

تاريخ التدقيق: 2026-11-21
النطاق: المستودع العام عند `v1.2.0`، فرع `main`، commit `4fd9715`، مقارنةً بوثيقة الرؤية التي قدمها مالك المشروع.

## الملخص التنفيذي

المستودع نموذج أولي منظم إلى طبقات .NET 8، لكنه ليس منتج نقل بيانات مكتملًا بعد. توجد واجهة WPF وخدمات ADB وتشفير ومحرك نقل مجزأ، لكن مسارات الاستخدام لا تصل بينها بصورة مكتملة، ولا يوجد مخزن نسخ احتياطية. أضيف Android Agent أولي للاقتران والمصافحة فقط. بُني لاحقًا إلى APK وثُبّت على هاتف Samsung SM-A135F (Android API 34)، ونجح الاتصال؛ لكنه لا يقرأ بيانات الهاتف ولا ينقلها. لذلك لا يصح توزيع المشروع على أنه ينقل بيانات المستخدم بأمان.

## الأدلة والحالة الابتدائية

- المستودع العام يحوي 10 commits والوسوم `v1.0.0` و`v1.1.0` و`v1.2.0`. لا توجد Issues مفتوحة ظاهرة وقت المراجعة.
- يحتوي الحل على Core وApplication وInfrastructure وInfrastructure.Security وStartup وCLI وWPF UI.
- سجل Git كان نظيفًا قبل التعديلات، وأُنشئ فرع محلي `codex/recovery-audit-completion` دون تغيير التاريخ أو دفع تغييرات.
- لا يوجد مشروع Android/Kotlin أو iOS أو اختبارات. ملف سير الإصدار في `docs/workflows/release.yml` وليس `.github/workflows`، لذلك لا يفعّل GitHub Actions تلقائيًا من هذا المسار.
- عند بدء التدقيق، انتهت محاولة NuGet بمهلة ولم تكن ملفات الاستعادة موجودة. بعد أن فعّل المستخدم VPN نجحت استعادة الحزم.

## النتائج ذات الأولوية في النسخة الأصلية `v1.2.0`

### حرجة — لا تستخدم في نقل بيانات حقيقية

1. `SecureTransferUseCase` لا يفتح الملف ولا يستدعي `ChunkedTransferEngine`؛ يعيد جلسة بحالة `Initiated` فقط. واجهة WPF تمرر المسار الثابت `selected_data.dat` وتعرض نجاحًا بعد رجوع الاستدعاء.
2. `AndroidSmsTransferService` يقرأ قاعدة SMS بامتياز root، ويكتب ملفات مرحلية إلى مسارات ثابتة. يولد مفتاح AES عشوائيًا ثم لا يحفظه ولا يرسله للمستقبِل؛ لا يمكن للجهاز الهدف فك البيانات. الأخطاء تُبتلع وتتحول إلى `Failed` بلا سبب ظاهر، والتنظيف غير مضمون عند الفشل.
3. `LicenseService.ValidateAsync` يقبل الترخيص دائمًا. `UpdateService` يعيد نتائج وبيانات وتوقيعًا وهميًا، ودالة التحقق تعيد `true` دون تحقق تشفيري. لا يجوز استخدام هذه الخدمات كضوابط أمن أو تحديث فعلية.
4. `ChunkedTransferEngine` لا يضمن الاستئناف الصحيح: لا يضبط موضع stream إلى الجزء المطلوب، ولا يعيد بناء SHA-256 للبادئة السابقة، ولا يتحقق من حدود رقم الاستئناف. لا توجد إعادة محاولة للأجزاء. الوسيط `ct` لا يصل لاستدعاءات النقل، و`isLast` غير مستخدم في بناء الإطار.
5. `ChunkedTransferEngine` يرسل الإطارات عبر `SendEncryptedPayloadAsync` ثم يبدأ `StreamDataAsync(RECEIVE_FRAME)` لكل رد. لا يوجد Android Agent في المستودع لإثبات توافق صيغة الرسائل أو ACK أو المصادقة.

### عالية

- `IDeviceRepository` مربوط بـ `MockDeviceRepository`، والاكتشاف لا يضيف الجهاز إليه؛ لذلك لا يستطيع مسار النقل العثور على جهاز مكتشف بهذا التسجيل.
- الاكتشاف يعمل في حلقة خلفية، و`StopDiscoveryAsync` يلغي `CancellationTokenSource` نهائيًا؛ لا يدار فصل الأجهزة أو ربط serial بمعرف ثابت. تحديث `ObservableCollection` يجري من callback دون `Dispatcher`.
- لا يظهر إعداد DataContext أو إنشاء `MainViewModel` في `App.xaml.cs`، مع أن XAML يعتمد على أوامر وخصائص ViewModel. لا يوجد مسار اختيار ملف حقيقي.
- `AdbService` يركب serial والمسارات والأوامر داخل وسيطات نصية، ويتجاهل exit code ولا يحدد مهلة أو إلغاء للعملية.
- `TcpAgentServer` يقرأ طول payload إلى `long` ثم يخصص مصفوفة به قبل التحقق من حد موجب وأقصى. صيغة الخادم منفصلة عن عميل Android ومحرك النقل.
- خدمة الاقتران تخزن رمزًا عالميًا واحدًا في singleton، دون تحديد معدل المحاولات أو ربط الرمز بجهاز/جلسة. ECDH موجود لكنه غير مربوط بمصادقة الطرف أو بروتوكول نقل.
- Workflow يحتوي خطوة توقيع صورية واسم إصدار/نصًا ثابتًا، ويطلب اختبارات غير موجودة. مساره الحالي لا يفعّل GitHub Actions.

### متوسطة

- `SmsNormalizationService` يعيد سجلين ثابتين ويتجاهل قاعدة البيانات.
- `MockTransferService` يزيد تقدمًا وهميًا بمهمة خلفية، بينما استعلام الحالة يعيد دائمًا `InProgress` ولا يوجد إلغاء حقيقي.
- السجلات تحتاج منع تسجيل نصوص الرسائل أو المفاتيح أو الحمولات.
- لا يوجد تخزين للنسخ أو سجل عمليات أو تقارير جزئية، ولا توثيق لحدود البيانات حسب Android/iOS.

## نقاط قوة قابلة لإعادة الاستخدام

- تقسيم الطبقات وعقود الخدمات أساس مناسب بعد إصلاح التسجيلات ومسارات الاستخدام.
- `HardenedEncryptionService` يستخدم AES-GCM بمفتاح 32 بايت وnonce عشوائي 12 بايت ووسم 16 بايت، لكن الخدمة وحدها لا تثبت أمان الجلسة أو تبادل المفاتيح.
- توجد بداية لمحرك أجزاء وتحقق SHA-256 ومهلة ACK، لكنها تحتاج بروتوكولًا متفقًا عليه واختبارات تكامل مع وكيل Android.
- WPF و.NET 8 يطابقان منصة التطبيق الأساسية في الرؤية.

## حدود التدقيق

هذا تدقيق للنسخة الأصلية `v1.2.0` ثم تحديثات فرع الاسترداد. تحقق اتصال أولي فعلي على Android 14، لكنه لا يثبت سلامة نقل بيانات لأن النقل غير منفذ. لا يمكن اعتماد نقل SMS أو جهات الاتصال أو iPhone دون تنفيذ واختبار على المنصات المقصودة ومراجعة الأذونات الرسمية.

## تغييرات السلامة في فرع الاسترداد

- أزيلت استجابة النجاح الوهمية لنقل الملفات؛ حالة الاستخدام الآن ترفض التنفيذ بوضوح ما دام Android Agent المتوافق غير متوفر.
- أزيل مسار الملف الثابت من واجهة WPF، واستُبدل بلوحة اقتران أولية توضح أن النقل غير متاح.
- أضيف بدء WPF عبر DI وربط `MainWindow` بـ `MainViewModel` وإيقاف خدمة الاكتشاف عند إغلاق التطبيق؛ شُغلت نافذة Release بصريًا.
- تعطلت عمليات SMS التي كانت تتطلب root وتفقد مفتاح فك التشفير، وأصبحت ترفض التنفيذ برسالة واضحة.
- أصبح الترخيص يفشل مغلقًا بلا خادم/تنسيق توقيع، وتعطلت فحوصات وتثبيت التحديثات بلا endpoint موثوق ومفتاح تحقق.
- أصبح اكتشاف ADB يحافظ على معرف الجهاز طوال جلسة التطبيق ويرسل أحداث الاتصال والفصل وتغيير الحالة، وتُحدّث الواجهة عبر WPF Dispatcher.
- أضيف مشروع `CrossPlatformDataTransfer.Tests` وفيه ستة اختبارات لحدود الأمان.
- بُني الحل كاملًا في Debug وRelease بنجاح (0 أخطاء و0 تحذيرات)، ونجحت الاختبارات الستة في كلا التكوينين.
- صُحح اسم أمر اكتشاف الأجهزة في XAML؛ الاختبار الرسومي أكد أن الضغط يحدّث رسالة الحالة. اجتاز إصدار الاقتران الأول اختبارًا على هاتف Android، لكن تحديث TLS الجاري لم يُختبر بعد على الهاتف.
- أضيف `android-agent` كتطبيق Kotlin أولي بخدمة foreground محلية ورمز اقتران مؤقت، مع أوامر `PAIR` و`PING` و`HANDSHAKE` و`GET_CAPABILITIES` فقط. لا توجد أوامر قراءة/كتابة بيانات.
- أضيف بروتوكول JSON بطول Big Endian وحد 1 MiB، وربطت شاشة Windows بمدخل الرمز والمصافحة. جُعلت عمليات streaming وإرسال الحمولة في عميل C# ترفض التنفيذ حتى يكتمل بروتوكول الملفات.
- أضيف Gradle Wrapper 8.13 من مصدر Gradle الرسمي، وطوبقت SHA-256 للـWrapper وتوزيع Gradle مع القيم المنشورة.
- اكتمل بناء APK Debug بعد تحديث إعداد Kotlin؛ بقي تحذير deprecation واحد في بناء إشعار Android. نجح إصدار الوكيل السابق في الاقتران والمصافحة على A13، لكن ذلك لا يثبت عمل تحديث TLS الحالي.
- الإصدار الحالي الذي يستخدم TLS ثُبت على SM-A135F (Android API 34)، لكن آخر محاولة لم تصل إلى مصافحة ناجحة لأن خدمة الوكيل لم تكن عاملة. لم يُختبر أي نقل بيانات لأن أوامر الملفات غير موجودة بعد.
- اجتاز `git diff --check` وفحص XML لملفات المشروع وXAML.

## تقدم لاحق للتدقيق الأصلي

- Android SDK Platform 36 وBuild-Tools 35.0.0 متاحان محليًا. أُصلح إعداد `compilerOptions` ليتوافق مع Kotlin Gradle Plugin 2.3.0.
- نُظمت مراحل الإنجاز في `TECHNICAL_ROADMAP.md`. أضيف نموذج أمان يستند إلى TLS القياسي، وشهادة مؤقتة من Android Keystore ومقارنة بشرية قبل الاقتران.
- أُعد تحديث Android بـ`SSLServerSocket` وWindows بـ`SslStream`، مع تأكيد رمز الشهادة على الطرفين. بناء Android نجح مع تحذير deprecation واحد؛ بناء Windows نجح بصفر أخطاء وتحذيرات في مجلد تحقق منفصل لأن نسخة الواجهة الحالية كانت مفتوحة.
- لم يُثبت تحديث TLS على الهاتف بعد، ولم يُنقل أي ملف. يلزم اختبار قبول/رفض رمز الشهادة على الهاتف قبل فتح ميزة الملفات.

## تقدم التحقق اللاحق — 2026-11-22

- ثُبت APK TLS الحالي بنجاح على هاتف المالك SM-A135F (A13، Android API 34)، وفُتحت شاشة التطبيق. لم يُثبت أو يُختبر أي هاتف آخر.
- شُغلت واجهة Windows من حزمة المعاينة، وتعرّفت على A13. لم تبدأ جلسة TLS الجديدة لأن مقارنة البصمة وموافقة المستخدم من الهاتف لم تكتمل بعد.
- كشف الفحص وجود نسختين من ADB (1.0.40 في `C:\\Windows` و1.0.41 ضمن Android SDK) تتنافسان على خادم ADB. عدّل التنفيذ لاختيار نسخة SDK وتجنب استدعاء shell عبر PATH.
- حُصرت واجهة ADB على اكتشاف الأجهزة، معلومات الطراز، وتمرير منفذ محدد للهاتف المختار. أزيلت منها أوامر root والنسخ المباشر للملفات.
- أزيل خادم TCP القديم الذي كان يقرأ إطارات دون TLS، وأوقف وضع CLI المرتبط به.
- نجح `dotnet build CrossPlatformDataTransfer.sln --no-restore` بصفر أخطاء وتحذيرات. اجتازت اختبارات الحدود الستة، ومنها رفض تدفق SMS المعتمد على root ورفض ادعاء اكتمال نقل ملف غير مدعوم.
- أُعيد بناء لوحة WPF بالعربية مع تقسيم مرئي لخطوات الاقتران وبصمة TLS، تكبير النافذة عند الفتح، فحص الأجهزة تلقائيًا، ورسالة حالة فارغة. بناء .NET نجح بعد التغييرات؛ لم يُجر اختبار واجهة/اتصال نهائي على الهاتف بعد.
- بعد أن أعاد المستخدم توصيل كابل A13، ظهر SM-A135F في قائمة Windows. كشف فحص الحالة أن خدمة Android Agent وتمريرة 4711 متوقفتان؛ لا يوجد حاليًا تحقق TLS أو نقل بيانات مكتمل.
